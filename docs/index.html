A field-tested method for instructing AI agents

Documentation-driven agents

The markdown is the program.

We don’t configure our grading agents in code. We instruct them — in a layered, version-controlled, self-correcting set of markdown files that load into the agent’s context automatically and override its default behavior. The rubric, the fairness rules, the audit protocol, and every hard-won lesson live in those files. The agents just read them.

This guide explains that system so you can build one for a new assignment — or for any recurring task you hand to an AI agent. It comes in two passes: a one-screen summary, then the detail — the file layers, the persistent memory, the write-back loop that makes the instructions compound, and the three things the docs encode (a deduction discipline, a verification harness, and an audit loop). The whole point: your instructions become a durable asset that gets smarter every time it’s used.

The one-screen version

Summary

An AI agent is only as reliable as the instructions in front of it, and a chat prompt evaporates when the session ends. So we treat instructions as infrastructure: files in the repo, loaded every session, refined every run. Three moving parts.

1 · Layered instruction files (CLAUDE.md). Markdown that auto-loads into context and overrides defaults. Layered by scope — general conventions at the repo root, assignment specifics one level down, the student-facing tutor prompt beside the assignment itself. Most-specific wins; general fills the gaps.

2 · Persistent memory. A per-user store that survives across sessions — an indexed set of single-fact files, so a fresh session already knows what happened last time and what you prefer.

3 · The write-back loop. The part that matters most. When the audit catches a failure, the fix isn’t just applied — a rule goes back into the docs, so that failure can’t recur next assignment. The instruction set compounds.

What those files encode is the actual grading method: a discrete-deduction discipline (every point removed is a named, evidenced claim), an independent audit harness (one reviewer per unit, blind to the rest), and a loop that ends only when a single pass is clean for the entire set at once. In one real run, that loop took five rounds — and three of its catches were errors inside a previous round’s fix.

Layer 1 — detail

The layered instruction files

Every session, the agent reads the CLAUDE.md files in scope before it does anything, and treats them as overriding its defaults. They’re plain markdown, checked into the repo, and organized so that the instructions get more specific as you get closer to the work.

your-project/
├─ CLAUDE.md                 ◆ root reviewer conventions — shared by every task
├─ task-01/
│  ├─ CLAUDE.md              ◆ this task’s specifics — criteria, sources, gotchas
│  ├─ shipped/CLAUDE.md      — (optional) instructions for a different audience
│  ├─ inputs/                — the material under review (read-only)
│  ├─ working-notes/<unit>/  — ledger · draft · audit-round{1..N}
│  ├─ output.md              ◆ authoritative output — fixed two-part format
│  └─ deliverables/          — final artifacts, produced only after the audit passes
└─ task-02/ …             — same shape; precedents carry forward

The load rule is simple and worth stating out loud: the most specific file in scope wins; more general files fill whatever it doesn’t say. The root file carries what’s true for all grading — the deduction rule, the report format, the audit protocol. The per-assignment file carries what’s true for this task — the point split, which files are the source of truth for verifying a claim, the per-task gotchas.

The trap: three files named CLAUDE.md, three different jobs

The most-copied warning in our root file exists because these look identical and mean opposite things. An agent that confuses them will apply the wrong rules to the wrong reader.

Repo root

Grader meta-conventions

Shared across all assignments. The deduction rule, the output format, the audit loop, accumulated precedent.

task-01/

Task specifics

Criteria, source-of-truth files to verify against, waiver rules, input naming. Everything the root file can’t know in advance.

shipped/

Student-facing tutor prompt

A different audience entirely — this one ships to students and tells the agent to be a Socratic tutor who never hands over answers.

When you’re grading, you are not the student’s tutor — so “never give answers” does not apply to the instructor’s questions. Naming the contexts explicitly, in the docs, is what keeps an agent from importing a rule from the wrong layer.

Output and working files are specified too

The docs don’t just set policy — they fix the shape of the work. The authoritative output has a mandated two-part format (an internal audit section, then the reader-facing deliverable), so every run is comparable. The working-notes/<unit>/ folders hold the agent’s artifacts — an evidence ledger, a draft, and one audit report per round — all versioned in git, so the reasoning behind a result is recoverable months later.

Layer 2 — detail

Persistent memory across sessions

The CLAUDE.md files are shared and per-repo. Memory is the complement: a per-user store that persists across sessions and projects, so a brand-new session doesn’t start from zero. It’s how the agent begins already knowing “the last run took four audit rounds,” “this one is finished,” or “the lead prefers to make the borderline calls personally.”

The mechanics are deliberately boring, which is what makes them reliable:

  • An index file (MEMORY.md) is loaded into context every session — one line per memory, so the agent knows what it knows.
  • Each memory is one file holding one fact, with frontmatter that says what it is and how to recall it.
  • A type field sorts memories into who the user is, how they want you to work, ongoing project state, and pointers to outside resources.
--- one file, one fact --- name: task-2026-q3-complete description: Q3 run finished — outcome, where things live, lessons metadata:   type: project // user | feedback | project | reference Q3 run completed 2026-07-11. Five review rounds to converge; outcomes never moved. Lesson banked: a fix is a new claim — re-verify replacements from scratch. Related: [[task-2026-q2-complete]] // memories link to each other

The discipline that keeps it useful: one fact per file, update instead of duplicating, delete what turns out wrong, and don’t store what the repo already records. Memory is for what you couldn’t reconstruct from the code and the git history — not a second copy of it.

Layer 3 — detail · the heart of the system

The write-back loop

Here is the property that makes the whole thing worth the effort. When a review catches a mistake, we don’t just fix the mistake. We add a rule to the docs so that class of mistake can’t recur — on this assignment or the next one. The instruction set is not written once; it is edited by its own failures.

Every rule in our root file exists because something went wrong once. The docs are a scar tissue of past mistakes — which is exactly why the next run doesn’t repeat them.
01A run hits a failure mode. An auditor credits the student with an idea the assistant actually suggested — a real, subtle attribution error.
02The immediate fix is applied and re-audited. That letter is corrected and the whole thing re-checked.
03A durable rule is written back into the docs. “Verify who typed an idea first against the raw record — and scan the log’s actual structure, not just the obvious field.” Now it’s standing policy.
04The next run’s agents are pre-warned. They read that rule before they start. The mistake that cost a round last time costs nothing this time.

You can watch the institutional knowledge accumulate in the file itself. Real lines now standing in our root conventions, each traceable to the run that earned it:

# excerpts — each is a scar from a prior run • Write cohort claims without factual universals — one counterexample fails the audit. • Revisions introduce errors at a high rate; re-audit whole units, not the flagged spot. • Props (praise) are ledgered as strictly as deductions. • Verify UI / behavior claims against the shipped code, not the session narrative. • A fix is a new claim, and inherits the counterexample. // re-verify from scratch

A prompt you retype each session can’t do this. A file can. That’s the case for treating instructions as version-controlled infrastructure rather than conversation.

What the docs encode · 1 of 3

The Discrete-Deduction Discipline

One rule the files impose on every score: every point you remove is tied to a discrete, named issue, with a one-line “how to avoid.” If you can’t name the specific thing the person did or failed to do, the points are awarded. A deduction is a claim, and a claim needs evidence.

Item 3: 18/20 — (−2) required section left blank;   the checklist marks it “skipped.”   How to avoid: the template offered four testable options — completing one earns it back. // no nameable issue on the other 18 points → earned, not “given”
  • Praise is audited as strictly as criticism. The counterintuitive lesson from checking our own work: most errors were overclaimed praise, not wrong deductions. So every quote and superlative in the “what you did well” paragraph is logged with its source, exactly like a deduction.
  • Ground truth beats memory, always. Every number or behavioral claim is verified against the source — the actual code, file, or record — never against recollection.
  • “What we owe you.” If your own instructions told the person X, you don’t penalize them for X, even when the system does Y. Decide up front which sources are authoritative for the subject and which are merely true.

What the docs encode · 2 of 3

The audit harness: independent fan-out

The person who writes an evaluation is the worst person to check it. So drafting and auditing are separate jobs, and the auditors are independent by construction: each is handed one unit of work and reads only that unit’s files — blind to the other evaluations and to each other. A claim can’t be “confirmed” by another unit’s data, and a detail borrowed from the wrong place has nowhere to hide.

Lead graderdrafts + normalizes
Auditor Areads only A
Auditor Breads only B
Auditor Creads only C
Auditor Dreads only D
Auditor Ereads only E

independent · fresh eyes each round · no shared context

Two supports make the fan-out work. The evidence ledger, written as the draft is written, logs every claim beside its source line — so auditing means checking each claim against what it cites, not re-deriving the evaluation. And a lead pass catches what isolation can’t: cross-unit consistency. In one run, an identical praise line was flagged in one letter and passed in another in the same round, because each auditor saw only their own. The lead grader greps the whole set for shared phrasings and applies the strictest verdict anywhere to every instance. Fan out for depth; one pass for coherence.

What the docs encode · 3 of 3

The loop, the condition that ends it — and the bound you also need

Audits find things; fixes get made; and then the fixes get audited again. The loop doesn’t stop when each unit has been clean at some point. It stops on one strict condition:

One pass comes back clean for the entire set at the same time.

That rule tells you when you may stop. It does not tell you what to do when the loop stops getting closer — and on a later run, it didn’t. Nine rounds. Blockers hit zero at round seven and stayed there; minor findings flattened and stopped falling. The diagnostic is one question:

What fraction of this round’s findings are in text that did not exist before the last round?

Seven of ten, on round nine. The loop had stopped measuring the work’s error rate and started measuring its own edit rate: every round made fixes, every fix was new text, and new text is where findings come from. A process that manufactures its own work does not converge, and running it again is not a plan.

The fix wasn’t a tenth round — it was to scope the exposure. Diff what actually ships. Most findings sat in internal notes nobody outside would ever read; of the material that reaches a reader, exactly two sentences had changed. One was a deletion, which can’t introduce a new claim. The other added one noun, checked against the source in a single search. Nine rounds of process, replaced by one diff and one check.

Two cautions: this applies only after blockers have sat at zero for several rounds — a loop still finding substantive errors is converging, however slowly. And scoping is a verification step, not a skip: the two changed sentences were still checked. What got dropped was the ceremony of a full pass, not the checking.

1Draft + ledger
2Normalize (lead)
3Audit (fan-out)
4Revise
5Re-audit whole unit
✓Clean for all at once → ship

if any unit fails, the set is not clean — revise and re-audit every touched unit again

  • Re-audit the whole unit, not the flagged spot. A revision changes the surrounding text and how it reads; checking only the edited line misses what the edit broke.
  • The human stays in the loop. Every round surfaces its findings and what changed; the judgment calls — borderline deductions, tone, whether a fix is acceptable — are the human’s, not the harness’s.

Then the part that matters most. A second person read the finished material once, cold, with no knowledge of the process — and found a defect that all nine rounds had passed, and that one round had examined and explicitly approved. The sentence predicted the work’s future influence in the world. Every reviewer had checked whether it was sourced, correctly attributed and consistent with the record; it passed all three, because a claim about what will happen later has no source to contradict it.

So: add the check the harness was missing — is this claim about the artifact, or about the world? — and keep one reader outside the loop. Not a better auditor. A different one, arriving once, without the process in their head. On both runs, that was the cheapest defect-per-hour in the whole method.

Across both runs — fourteen rounds and seventy independent reviews — not one finding changed an outcome. Every one was a grounding or phrasing defect. If your loop is meant to protect the result, measure whether it ever has; if it only protects the prose, size it accordingly.

Take it with you

Set this up for your own work

None of this is specific to grading. It fits any recurring, high-stakes task you hand to an AI agent — code review, a compliance or security audit, report QA, contract review, release notes — anywhere a plausible-but-wrong result is expensive and the task will come around again. The setup:

  1. Stand up the file tree. One repo, a root instruction file, a folder per instance of the task, working-file and output conventions. Version everything in git.
  2. Seed the root conventions. Write down what’s true for every run: the standard for a finding, the output format, the review protocol. Keep it general; the specifics go one layer down.
  3. Write the per-task file — and name your ground-truth sources. The criteria for this task, and exactly which files or systems are authoritative for verifying a claim. Separate what’s authoritative from what your subject was entitled to rely on.
  4. Fix the working-file shape. An evidence ledger (claim + source, written as you draft), a defined output format, one review file per round. Make the reasoning recoverable.
  5. Turn on memory for continuity. Let a fresh session start knowing the last run’s state and your standing preferences, without re-explaining.
  6. Run the harness and the loop. Independent reviewer per unit, blind to the rest; a lead pass for cross-unit consistency; re-audit whole units; stop only on one clean pass over everything.
  7. Write every lesson back into the docs. This is the step that makes it worth doing. Each failure becomes a rule; the instruction set gets stronger every run instead of resetting to zero.
  8. Keep a human on the judgment calls, and keep the trail. What changed, and what it changed from, is the audit record — it’s how a later reader trusts the result.

Working solo, or without a multi-agent setup?

The instruction files and memory work with a single agent — the layering and the write-back loop are the valuable parts, and neither needs a fleet. You can even be your own auditor: draft, let it rest, and return as a stranger who must verify every claim against its source with no memory of writing it. The ledger is what makes that honest — “re-checking” means checking sources, not re-reading your own reasoning.
